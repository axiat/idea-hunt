# 任务接口

## 状态与任务

运行根 `状态.json` 保留既有字段，并增加 `harness_control`：`schema_version=1`、`epoch`、`paused`、`permissions`、`tasks`、`recoveries`。`tasks` 以 `task_id` 为键，记录任务文件的 `ref(path, sha256)`、`agent_id`、`stage`、`status`。`permissions` 使用 `allowed_actions` 与 `denied_actions` 数组表示本运行既有授权，不替代真实工具权限，也不产生新授权。`recoveries` 的登记键采用 `<原task_id>/<failure_id>`。活跃运行使用 `status=running` 或 `active`，仅表示运行登记为活跃，动作许可仍由当前暂停、权限与任务校验确定。科学任务是否实际启动、形成原文或改变判断，分别依据任务事实、完整材料和具名阶段结论确认，具体研究阶段另列。

任务状态为 `registered`、`delivered`、`accepted`、`started`、`completed`、`failed`、`stopped`。输入排队、实际收件、接受和实际启动分别记录 `delivery_enqueued_at`、`delivered_at`、`accepted_at`、`started_at`；旧平铺材料事实继续保留和校验，新输出使用独立 `output_delivery`。

任务 envelope 的最小字段为 `schema_version`、`run_id`、`epoch`、`task_id`、`stage`、`role_ref(path, sha256)`、`agent_id`、`task_scope`、`input_refs`、`output_dir`；`run_id` 使用运行目录名，输入引用记录路径及 SHA-256，来源合同和故障恢复按需增加 `contract_refs`、`recovery_of`；新科学任务在派发前增加下述 `scientific_work_ref`，历史任务不追溯增加。任务目录以 envelope 声明的本次运行组目录为准。派发内容须明确阶段、输入、允许操作、阶段限额和交付位置；来源核验与构想发现使用各自的任务及完成条件。

`task_scope` 使用 `allowed_actions`、`allowed_stages` 数组及 `limits` 对象；`allowed_stages` 包含当前 `stage`，`limits` 按动作记录非负整数限额。支持的动作是 `read_local`、`preserve_local`、`generate_local`、`read_cache`、`source_get`、`source_query`；任务允许动作须符合根授权，来源动作另须有有效 `contract_refs`。`read_cache` 指来源席依据合同交付缓存，须核账户及合同；组内读取已合法交付、被任务引用的本地材料使用 `read_local`，不会触发新来源获取。`contract_refs` 仅绑定本任务实际承担的 `source_get`、`source_query` 或 `read_cache` 合同；本地材料的来源出处与历史关联保留在 `input_refs` 或科学原文。来源 hold 仅阻止依赖该运输的动作，独立且已获授权的本地任务按自身 scope 核验；显式附入 `contract_refs` 的合同仍完整校验。这些声明仍受真实用户限制及工具权限约束。零额度阻止对应动作；本地正限额只核对已记录的 `action_used`，实际读取与写入次数由任务负责成员如实记录，校验器不自动计数。未知 scope 字段返回 hold。根任务记录保持紧凑引用与路由；额外重复副本仅在实际存在时核对一致性，无需为校验增加副本。

## 科学合同

新科学任务在派发前通过 `scientific_work_ref` 显式采用；引用的 path/hash 须与 `input_refs` 中一个已有 JSON 输入相同，合同位于该 JSON 的 `scientific_work`。新合同版本为 `schema_version=2`；既有 v1 及其原引用保持。`decision_question` 为非空字符串，三个前提字段严格为字符串数组，三个结果字段严格为非空处置字符串。`deliverable` 使用 `format="message"` 或 `format="markdown"`、非空 `version`、实际接收组长的 `reader_id`，并以 `delivery_plan` 声明可执行交付。历史未显式采用合同的任务不追溯增加要求，已有输入包含同名数据也不自动启用合同。

已有输入 JSON 的合同结构如下，占位值由实际任务填写，前提数组允许为空。

```json
{
  "scientific_work": {
    "schema_version": 2,
    "decision_question": "<待改变的具名命题判断>",
    "premises": {
      "required_facts": [],
      "allowed_assumptions": [],
      "deferred_unknowns": []
    },
    "outcome_routes": {
      "supported": "<支持时的处置>",
      "refuted": "<反对时的处置>",
      "unknown": "<仍未知时的处置>"
    },
    "deliverable": {
      "format": "markdown",
      "version": "<约定版本>",
      "reader_id": "<实际接收组长ID>",
      "delivery_plan": {
        "mode": "direct",
        "target": "小组/<组号_主题>/科学稿_v01.md"
      }
    }
  }
}
```

文件交付 `delivery_plan` 的 `target` 为本运行内的 Markdown 原件路径，相对路径从运行根解析；声明路径及解析目标均须位于本任务的 `output_dir` 内，路径不能包含 `..`。dispatch 与 entry 在科学工作开始前核验交付权限及已记录的动作余额，实际工具权限仍由调用者确认。

- `direct` 严格包含 `mode`、`target`；本任务须允许 `generate_local` 和 `preserve_local`。
- `delegated-archive` 严格包含 `mode`、`target`、`archive_task_id`、`archive_agent_id`。`archive_agent_id` 须等于 `reader_id`；引用组长已登记、同 epoch、路由与引用有效且未进入终态的任务，两个任务的 `output_dir` 须为同一声明路径及解析目录。归档任务须允许 `read_local` 和 `preserve_local`，继续受根授权、既有拒绝及余额约束。同阶段归档可复用组长已有任务。

作者仅允许消息而接收组长明确允许报告文件保全时，可以采用第二种文件计划；双方均仅允许消息时使用完整原生消息计划。文件计划示例，例如将上述 `delivery_plan` 替换为以下对象。

```json
{
  "mode": "delegated-archive",
  "target": "小组/<组号_主题>/科学稿_v01.md",
  "archive_task_id": "<组长已有同组任务ID>",
  "archive_agent_id": "<实际接收组长ID>"
}
```

既有 v1 科学合同未声明 `delivery_plan` 时，dispatch 与 entry 按直接交付核验，缺少相应权限返回 hold。新登记输出仍须位于任务 `output_dir`；声明计划后还须与 `target` 一致。checkpoint 及历史完成原件的复用仅保全旧引用，不追溯增加交付准入要求；对已经登记的同版本同原件追加实际实读事实可沿用原位置，新增或更换原件仍严格核验目标目录。完成始终依赖实际交付、归档和对应全文实读。

### 完整原生消息与实际交付确认

消息合同使用 `schema_version=2`，`deliverable={"format":"message","version":"v01","reader_id":"<实际组长>","delivery_plan":{"mode":"native-message"}}`。作者需要 `read_local`、`generate_local`，消息方式不要求报告文件写入或 `preserve_local`。声明 scope 继续受根授权、历史拒绝及真实会话约束限制。

每个科学任务在 dispatch/entry 前须有 `delivery_readiness_refs`，按作者、接收组长顺序提供两份原生 SendMessage 定位，接收地址为根 `total_leader`。完整 JSON 正文采用：

```json
{
  "kind": "delivery_readiness",
  "run_id": "<运行目录名>",
  "task_id": "<任务ID>",
  "epoch": 2,
  "agent_id": "<本条实际确认人>",
  "author_id": "<作者>",
  "reader_id": "<实际组长>",
  "format": "message",
  "version": "v01",
  "delivery_plan": {"mode": "native-message"},
  "allowed": true,
  "checked_at": "<带时区的实际确认时刻>",
  "constraints": "<与本路径有关的实际会话限制摘要>"
}
```

Markdown 路径同样需要这两份确认，`format` 与 `delivery_plan` 绑定真实文件路径及归档人。字段中的 true 是实际角色的具名声明，须核原生发送者，不能由组长代作者填写；工具无法证明其对私有会话指令的解释正确。约束变化后重新确认并保留旧记录；限制未知或冲突返回 hold。

`message_ref` 严格包含 `source`、`author_id`、`reader_id`、`task_id`、`version`。`source` 使用消息归档节的完整定位，额外必需 `tool_use_id`；仅支持完整 `/message/content/<n>/input/message` 叶，要求原生 `agentId` 与作者相同，实际 `SendMessage.input.to` 与组长相同。正文、行指纹、UUID、tool ID、版本及身份全部绑定；没有原生作者标识的记录保持待核，定位声明不能充当作者认证。根 owner 根据实际工具上下文与原生存储位置登记 `harness_control.native_message_bindings={"<真实actor>":["<已观察的规范化原生转录绝对路径>"]}`；任意其他文件即使自填相同 `agentId` 也不能冒充该 actor 的原生消息。绑定不授予文件写入或来源权限。程序只返回必要检查结果，组长及后续科学角色负责全文实读。`message_input_refs` 可在 envelope 中显式列出后续任务获准读取的完整消息原件，文件 `input_refs` 仍保持原格式。

消息 `output_delivery` 使用 `message_ref` 代替 `material_ref`，包括 `version`、`formed_at`、`retained_at`，实际投递使用 `delivered_at` 或 `received_at`，全文实读使用 `read_at`、`reader_id`、`read_version`、`read_message_ref`。`received_at` 是实际确认收到完整正文的观察时刻，精确运输到达时间可继续未知。`producer_receipt_ref` 与 `read_receipt_ref` 指向作者及组长分别发送给根 owner 的完整原生 JSON 叶：前者为 `{"kind":"scientific_delivery","message_ref":...,"version":"v01","formed_at":...}`，后者为 `{"kind":"scientific_read","message_ref":...,"version":"v01","read_at":...}`。元信息收据自身不替代被引用正文。完成需实际启动、原生正文、两份身份绑定收据、全文交付确认、保全和实读全部通过；不会生成报告文件。`checkpoint.saved_messages` 追加保存消息引用，既有 `saved_refs` 保持。

### 显式交付协议修订

根 `harness_control.delivery_protocol_ref` 引用暂停下形成的 JSON，包含 `schema_version=2`、`run_id`、递增的 `from_epoch`/`to_epoch`、`norm_archive_ref`、当前 `norm_refs` 和 `task_mappings`。每项映射严格为 `task_ref` 及可选 `deliverable`、`delivery_readiness_refs`；`task_ref` 精确绑定旧 envelope 路径和 SHA。新交付保持原版本与原接收组长，科学问题、前提和三种处置继续读取原 `scientific_work_ref`。原 envelope、输入和历史 epoch 均不回写；原已启动任务保持原启动事实，未启动任务经当前有效 epoch 的检查后正常派发。新 entry 收据的 epoch 是当前有效 epoch。

归档采用既有白名单 ZIP 合同。映射的归档回退仅适用于 skill `SKILL.md` 与 `参考/任务接口.md` 的精确旧原字节，当前规范仍核 hash；不能以此改写科学判据、资源、权限、来源账或限制。映射既有稿时保留旧原件及许可异常，通过作者和组长的新原生收据验收同版正文，不重做科学或追认旧文件许可。根暂停与恢复由 owner 在用户授权下管理，薄生命周期工具不修改这些控制字段。

## 只读检查

公开接口为 `check_task(run, task, phase, *, checkpoint_archive_ref=None) -> (exit_code, result_dict)`，接受 `str` 或 `Path`，无 stdout、无写入，并自行拒绝非法 phase；JSON 引用的 `path` 仍须为字符串。CLI 保留 JSON 结果与退出码 `0=allow`、`1=fail`、`2=hold`。成功的 entry 在末尾读集 hash 重核通过后返回 `result.receipt`，原 check CLI 的 JSON 也包含同一 `receipt`；其中 `checked_at` 由校验器记录真实执行时刻，快照与绑定字段来自本次实际读取。调用方原样传递该对象，登记实际启动的 `occurred_at` 另取真实启动证据。

```text
python3 -I -B <skill>/脚本/任务校验.py check --run <运行目录> --task <任务文件> --phase dispatch
python3 -I -B <skill>/脚本/任务校验.py check --run <运行目录> --task <任务文件> --phase entry
python3 -I -B <skill>/脚本/任务校验.py check --run <运行目录> --task <任务文件> --phase checkpoint
```

`dispatch` 与 `entry` 核验暂停、epoch、有效任务、路由、作用域及引用。新 entry 及 start 须有实际 `accepted_at`，满足 `delivered_at <= accepted_at <= started_at`；仅 delivered 或 accepted 标签不能替代接受事实，也不能生成可用于启动的 entry 收据。历史 checkpoint 保留未知接受时间，不追填时间。`checkpoint` 允许暂停保全，不授权研究或来源运输。

旧任务缺少真实停止证据导致 hold 时，`check` 额外返回 `execution_blocker`，包含原 `task_id`、`agent_id`、`task_ref`、`recorded_runtime_id`、`required_evidence` 及 `unknown_is_not_evidence=true`。调用者据此定位原任务并取得真实证据，缺少 runtime 或完成标签不能推断已经停止。

普通同 agent 复用在 dispatch/entry 时独立核验旧终态：stopped/failed 须有 runtime 及精确真实停止收据，记录为 runtime_state=stopped，已知启动、停止时刻与收据一致；缺证明 hold，已知冲突拒绝。completed 须验证旧 envelope 对应的交付事实及显式采用的科学合同，终态标签本身不足以释放角色。存在 failure_id 时，逻辑恢复链与拒绝事实仍须满足原要求，停止事实不替代恢复登记。checkpoint 不追加上述普通复用门槛，原有权限、来源、恢复及保存点核验继续执行。终态收据接受 `finished_at` 或 `finished_at_utc`，均须带时区；两者并存时须表示同一时刻，原收据保持原文。

暂停保全任务可以采用以下字段值，其他最小字段、路径与 hash 须完整填写并登记；根授权须已允许 `read_local` 和 `preserve_local`。此任务仅供保存点检查，不能进入派发或研究入口。

```json
{
  "stage": "checkpoint",
  "task_scope": {
    "allowed_actions": ["read_local", "preserve_local"],
    "allowed_stages": ["checkpoint"],
    "limits": {"preserve_local": 1}
  }
}
```


薄任务工具登记新任务时初始化 `checkpoint={"saved_refs":[],"missing_sections":[]}`。记录输出时，仅将实际通过 hash 核验的 `output_delivery.material_ref` 去重追加到 `saved_refs`，既有引用与 `missing_sections` 全部保留。已观察或交付的科学原件按版本保留，新版使用不同路径；未形成、未观察的工作草稿可编辑，`checkpoint.saved_refs` 保留实际保全版本，旧引用已被覆盖时须在提交前拒绝。空缺段数组仅表示未登记已知缺段，不能证明科学完整；工具不推断缺段、产物或实读。暂停后沿用 `check --phase checkpoint` 检查已记录材料保全。

### 历史规范保存点

旧任务引用的规范原路径发生升级后，可为 checkpoint 显式传入 `checkpoint_archive_ref={"path": "<归档路径>", "sha256": "<归档整体SHA256>"}`。CLI 的两个归档参数须配对提供，三参 API 调用及原退出码保持兼容。

```text
python3 -I -B <skill>/脚本/任务校验.py check --run <运行目录> --task <旧任务文件> --phase checkpoint --checkpoint-archive <历史规范归档.zip> --checkpoint-archive-sha256 <归档整体SHA256>
```

归档采用 `快照清单.json` 的 v1 schema：`schema_version=1`、`purpose`、`files`；每项严格包含 `source_path`、`archive_path`、`bytes`、`sha256`。整体 ZIP、清单唯一性、合法成员名、成员字节数与 SHA 均须通过核验；ZIP 只作为数据读取，不解压或执行。整体及成员解压后总量各最多 8 MiB，单成员最多 1 MiB，清单至多 32 个文件，额外或重复成员拒绝。

公开版本附带合成归档测试，实际历史快照由运行 owner 自行保全。归档白名单中的工作区固定为当前用户的 `~/research/机器人选题`，skill 路径由脚本实际安装位置解析；自定义工作区的规范暂不支持归档回退，普通任务校验仍支持自定义工作区。`评审校准.md` 使用同一固定路径白名单及原字节 hash 核验。

历史解析仅作用于任务 `role_ref` / `input_refs` 中精确匹配的已知规范：本 skill 的 `SKILL.md`、`配置.yaml`、`参考/任务接口.md`，任务校验、任务变更、消息归档三份脚本及其对应测试，以及研究工作区的 `AGENTS.md`、`判定标准.md`、`评审校准.md` 和 Leader、组长、调研人、初筛人、审稿人五份角色文档。`source_path` 使用未 resolve 的绝对原路径精确匹配，链接别名或其他路径不能借解析目标匹配冒名。当前字节不再匹配任务旧 hash 时，才使用清单中具有同一 source_path 与 hash 的历史成员；结果的 `checkpoint_archive` 列出实际使用的归档、成员与 hash，并附 `checkpoint_archive_norm` 诊断。

归档不适用于 dispatch/entry，也不为 Root、任务 envelope、权限限制、来源账与合同、停止收据、科学输入或输出提供通用回退；显式 `scientific_work_ref` 也不获得历史规范解析。归档文件、原引用路径绑定与当前读取内容均参与末尾复核。未提供归档时继续执行原 hash 检查；错 ZIP、错整体或成员 hash、未知规范及检查中变化均拒绝。旧任务及其 norm hash 保持原文，归档通过仅表示材料可保全，不授权恢复研究。

## 有界查询

有界查询的 Python 接口为`inspect_run(run, task=None, status=None, agent=None, limit=20, cursor=None)`；CLI 支持以下参数。

```text
python3 -I -B <skill>/脚本/任务校验.py inspect --run <运行目录> [--task <任务ID或路径>] [--status <状态>] [--agent <真实ID>] [--limit 20] [--cursor <返回的next_cursor>]
```

`control.effective_paused` 与 `pause_reasons` 共同反映根状态、`harness_control.paused`、优化暂停及 `draining_existing_tasks`，与派发准入使用同一暂停判断；根 `status` 或单独的 `paused` 字段不能替代该结果。

每项任务返回 `work_kind=scientific|source|administrative_or_legacy`，仅按显式科学合同及声明的来源动作分类，历史材料的科学性质仍由原文确定。`recorded_facts` 保留输入收件、接受、启动、输出形成、交付、归档、实读时刻，以及 `runtime_state`、`runtime_id`、`stop_receipt_ref`、`unstarted_cancelled_at`。缺失事实保持未知。

`progress` 使用 `scope="returned_tasks_only"`、`physical_activity="not_checked"`，并给出 `scientific_task_records`、`scientific_started_records`、`scientific_output_records`。计数仅覆盖本返回页中显式采用科学合同的任务、已登记 `started_at` 的任务及具有输出引用的任务，不能证明进程仍在运行、产出已实读或科学评级成立。

查询默认 20 条、最多 100 条，整个 UTF-8 输出不超过 12288 B。结果返回 `root_sha256`、实际读取快照的 `snapshot`、筛选后的 `total`、`truncated`、`next_cursor`，以及运行控制、所选任务的路由、必要引用、输出版本与缺段摘要；累计账及科学全文保持原位置。分页沿任务 ID 稳定排序，cursor 绑定 `root_sha256`、筛选项与页长；根状态或筛选改变时重新查询，每页重新校验选中任务引用。`snapshot` 汇总本次实际读取的文件路径与 hash 集合，可能随页变化，不能代替分页使用的根版本。`action_permission=false` 明确表示 inspect 不产生动作许可，受限动作仍须 check。

## 任务变更

根 owner 使用独立的`脚本/任务变更.py` 登记任务生命周期，默认 preview，显式 apply 才写入；成员提交变更请求，模型无需临时编写根状态更新代码。变更仅覆盖任务登记、实际收件与接受、实际启动、已形成输出及对应实读、完成、失败、真实停止，以及有独立观察证明的未启动任务行政撤销。调用须提供预期根 hash、真实身份及可定位证据；实际发生时刻来自证据，工具只生成 `recorded_at`，未知项保持未知。CLI 的 `--owner` 须匹配根状态 `total_leader`，主线程实际 owner 为 `main` 时填写 `main`。相同事实重放无变更，冲突、乱序或终态复活均拒绝；`failed` 与有运行时证据的 `stopped` 分列。

读集同时保留原始绝对路径到解析目标的绑定及目标内容 hash，覆盖文件链接、父目录链接和调用时的运行/任务入口。固定链接可正常使用；重复读取或返回成功、提交前发生改指均拒绝。Gate、inspect、嵌套 entry、prepare 与原子替换前共用读集重核，嵌套 entry 的内容与路径绑定一并合并；该检查不声称形成操作系统级原子快照或约束非合作外部写入者。

apply 沿用根 owner 单写与路由检查，使用合作锁、预期 hash、锁内读取、提交前原字节比较及同目录原子替换；合作锁不能约束外部非合作写入者。工具仅修改目标任务的登记与生命周期字段，来源账户与合同仍由来源 owner 管理，权限、epoch、暂停、goal_met 及恢复历史均不能经此修改。事实登记不产生派发许可，工具不创建 agent、不投递消息或执行来源运输；读写入口分离，只读校验器保持无写入。

```text
python3 -I -B <skill>/脚本/任务变更.py --run <运行目录> --owner <根owner> --expected-root-sha <已读根SHA256> --events <事件JSON>
python3 -I -B <skill>/脚本/任务变更.py apply --run <运行目录> --owner <根owner> --expected-root-sha <已读根SHA256> --events <事件JSON>
```

事件文件严格采用 `{"events":[...]}`，单批 1–20 项；模式省略时为 preview，也可显式写 `preview`。同一真实消息中确认的实际收件与接受可按事实顺序放入同一批，例行 ACK 复用原任务及证据；实际启动仍须先取得已提交前置事实对应的 entry 收据。每个事件共同包含 `event_id`、`type`、`task_id`、`agent_id`、`stage` 和带时区的 `occurred_at`，并在 `evidence_ref(path, sha256)` 与内嵌 `evidence` 中恰选一项，按事件类型增加以下字段。

| type | 增加字段与实际含义 |
| --- | --- |
| `register` | `task_ref` 引用待登记 envelope。 |
| `input_observed` | `status=delivered` 或 `accepted`；先确认收件，再确认接受。 |
| `start_observed` | `runtime_id`，以及 `entry_receipt_ref` 或内嵌 `entry_receipt` 恰一项；记录已有实际启动。 |
| `output_observed` | `output_delivery`；记录已有输出与交付事实。 |
| `complete` | 无额外字段；确认实际启动后的任务完成。 |
| `cancel_unstarted` | `unstarted_receipt_ref(path, sha256)`；追加未启动撤销标记，原任务状态与历史保持。 |
| `terminal_observed` | `status=failed` 须有 `failure_id`；`status=stopped` 须有 `runtime_id` 与 `stop_receipt_ref`，`failure_id` 可省略，已有值保留，显式冲突拒绝。 |

暂停前已启动但启动事实迟报时，可凭精确绑定任务、agent、runtime、停止状态、成功结果与时刻的完整真实停止收据补全缺失的 runtime 绑定并直接保全停止事实；已有 runtime 不一致时拒绝，`started_at` 未知时保持空缺，暂停 entry 仍拒绝，这仅保全实际停止状态，不计任务完成或研究许可。既有逻辑状态为 completed 或 failed 时，仅追加 `runtime_id`、`runtime_state="stopped"`、`stopped_at` 和 `stop_receipt_ref`，原逻辑状态及失败身份、事实保持，completed 记录不新增 `failure_id`；其他未完成任务才将逻辑 `status` 置为 stopped，运行时停止记录不复活工作。真实停止时刻可早于后来登记的科学完成或实读；stop 核验已知 `started_at` 的时间下限、既有停止事实的冲突或幂等，以及收据精确绑定，其他生命周期的乱序保护保持。实际停止仍填写真实 `occurred_at`，观察与记录时刻分别保存为 `observed_at`、`recorded_at`。

真实 `terminal_observed(status="stopped")` 可为 legacy stopped 追加缺失的 runtime 与停止收据，保留原状态及失败身份。仅该停止事件与 `cancel_unstarted` 允许旧任务 `epoch <= 当前epoch` 的纯行政保全；登记时不重新认证已变化的旧角色规范或科学输入内容，原 envelope、hash、owner、CAS、停止或撤销收据，以及已有输出与保存引用的 hash 继续核验。此例外不扩展到 register、start、complete 或 failed，不产生研究恢复许可。

`evidence_ref` 指向已有 JSON，包含 `observer_id` 和 `event`；该文件若另有 `observed_at`，也须满足 `observed_at >= occurred_at`。内嵌 `evidence` 则严格包含 `kind="message"|"tool"`、可定位的 `id`、实际 `observer_id`、带时区的 `observed_at` 和 `event`，且 `observed_at >= occurred_at`。两种证据的 `event` 均须精确等于本事件去掉 `evidence` 与 `evidence_ref` 后的内容。已观察消息或工具回执可直接内嵌，例行 ACK 复用原任务记录，无需逐次新增证据文件。证据须来自真实消息、工具或文件观察；工具仅核验 owner 已观察声明的结构，不能证明事件真实发生或阅读者已经理解。`output_observed` 包含 `read_at` 时，证据的 `observer_id` 须等于 `output_delivery.reader_id`，由实际接收角色确认实读；其余事件填写实际观察者。

`entry_receipt_ref` 保存的对象或内嵌 `entry_receipt` 均直接采用成功 entry 返回的 `result.receipt`，其字段包含匹配的 `task_id`、`agent_id`、`stage`、`epoch`、`phase="entry"`、`decision="allow"`、`ok=true`、entry 实际检查对应历史根快照的 `root_sha256`、当前 envelope 的 `task_sha256` 和带时区的实际 `checked_at`，且 `checked_at <= occurred_at`。历史 `root_sha256` 核验为 64 位小写十六进制，根状态发生无关更新不使旧检查事实失效；当前任务 hash、epoch、身份与路由仍须一致。工具重新执行当前 entry 核对暂停、权限及来源限制，并以本次 CAS 确认根状态未并发变更；历史收据不产生当前启动许可。事件保存在原任务 `lifecycle_events`，完整 `event_id` 与内容一致的重放无变更，内容冲突拒绝。


legacy completed 首次登记 `output_delivery` 时，旧平铺 `material_ref`、`formed_at`、`delivered_at` 须足以确认已完成原件；新声明须匹配其解析路径与 SHA、已有版本以及已知形成、交付、归档、实读时刻与读者。已知版本包括现存 `version`、`material_version`、`output_version` 字段；这些字段存在时须一致。字段不足时 hold，`checkpoint.saved_refs` 不能单独指定当前输出；同原件的迟到实读等缺失事实可追加，旧字段与引用保持。已结构化 completed 的原件和版本继续不可替换，文件与 hash 由 observe/prepare 核验，纯 reducer 不读取文件。

### 未启动任务撤销

`cancel_unstarted` 沿用已有事件共同字段、证据、`update_tasks` 及 CLI，仅向原任务追加 `unstarted_cancellation={receipt_ref, cancelled_at}` 和本次生命周期事件。`receipt_ref` 为事件的 `unstarted_receipt_ref`，`cancelled_at` 为真实 `occurred_at`；原 `status`、失败、输出、来源、权限、epoch、暂停与 `goal_met` 保持，行政撤销不生成 runtime 停止事实。已撤销原任务的 dispatch 与 entry 拒绝，checkpoint 仍可保全。标记通过原生校验后，同一 agent 可接受普通新任务，无需为该准备件提供 runtime 停止事实；此例外仅解除该准备件的在途占用，旧拒绝汇总、当前根权限、暂停及新任务的完整 dispatch/entry 检查继续适用。

收据严格使用 v1：`schema_version=1`、`run_id`、`task_id`、`task_sha256`、`epoch`、`agent_id`、`stage` 精确绑定旧 envelope；`status="not_started"`、`success=true`、`cancelled_at`、`confirmed_by=<根owner>`，并保存该任务原生未通过 dispatch 的 `dispatch_check_report`。`delivery_enqueued`、`delivered`、`accepted`、`started`、`pending_delivery` 均为 `false`，`source_actions_executed=0`。独立观察保存在 `observation={kind, id, observer_id, observed_at}`，`kind` 为 `message` 或 `tool`，`id` 须可定位，`observer_id` 与事件的实际观察者均须为根 owner；`observation.observed_at >= cancelled_at == occurred_at`。

根 owner 须实际确认不存在排队或迟到投递。该路径仅支持原 `registered` 或 `stopped`、无 `failure_id` 的准备任务；已有派发、接受、启动、runtime、非零动作或科学输出等矛盾事实时拒绝，已有 dispatch 报告及 false/zero 声明须与收据一致。`material_ref` 可以保留原 envelope 准备件，其引用不视为科学输出。旧 epoch 不高于当前 epoch 时，仅可登记该行政事件，旧规范及科学输入引用保持原文。

`registered` 标签、缺失字段、SDK completed 或 `No task found` 均不能证明未启动，缺少独立观察时继续 hold。已实际启动的任务沿用真实停止与故障恢复规则；同一 `task_id + failure_id` 的一次有限恢复要求保持。

### entry 收据串接

start 所依赖的 register、实际收件及实际接受事实须先经 apply 提交，再对已提交状态实际执行 entry。同批尚未提交的前置事实不参与 entry 检查，不能充当已允许启动的证明。Python 写入口为 `update_tasks(run, owner, expected_root_sha, events, apply=False)`；成功 entry 的原生收据可直接用于后续启动事件。

```python
entry_code, entry_result = check_task(run, task, "entry")
if entry_code != 0:
    raise RuntimeError(entry_result)
entry_receipt = entry_result["receipt"]
```

角色在 entry 成功后实际启动并返回可定位证据。`actual_start_fields` 为该真实启动事件的六个共同字段及 `runtime_id`；`actual_observation` 为实际消息或工具观察的 `kind`、`id`、`observer_id`、`observed_at` 四项，实际发生与观察时间分别填写。调用方将上述原生收据原样附入事件，再查询当前根版本提交 preview。

```python
start_event = dict(actual_start_fields)
start_event["entry_receipt"] = entry_receipt
start_event["evidence"] = {
    **actual_observation,
    "event": dict(start_event),
}
inspect_code, current = inspect_run(run, task=task, limit=1)
if inspect_code != 0:
    raise RuntimeError(current)
preview_code, preview = update_tasks(
    run, owner, current["root_sha256"], [start_event]
)
```

preview 核对通过后，根 owner 显式 apply 同一事件与预期根 hash；若期间根状态变化，重新读取并处理 CAS 冲突。采用 CLI 时同样直接消费 entry JSON 的 `receipt`，内嵌为 `entry_receipt` 或保存原对象后以 `entry_receipt_ref` 引用，绑定元数据与检查时刻均保留程序原值。

## 输出收据

文件 `output_delivery` 的必填字段为 `material_ref(path, sha256)`、`version`、`formed_at`；后续按已发生事实增补 `delivered_at`、`archived_at`、`read_at`。实际阅读收据同时填写 `reader_id`、`read_version`、`read_material_ref`，后两项须与当前输出版本及完整材料引用精确相同，时刻均须带时区。同版本与引用只追加事实；更换版本或 hash 后重新取得实读，已 completed 的材料保持原文。所有 completed 任务记录均须有实际 `delivered_at`；使用 `output_delivery` 的任务还须有输出 `delivered_at`，未使用该结构的 legacy 记录须保留 `formed_at`、`material_ref` 及平铺交付事实。行政输入的 delivered/accepted 标签不充当输出交付。显式采用科学合同的任务另外要求约定版本与接收组长一致；文件方式要求非空 Markdown 原件、归档及实际阅读，消息方式要求完整原生正文、保全、身份绑定与对应实际阅读；历史任务不追溯强加科学实读要求。


### 消息原文归档

`脚本/消息归档.py` 仅保全实际已观察的完整消息文本，Python 入口为 `archive_message(run, task, actor, expected_root_sha, source, apply=False)`，返回 `(exit_code, result_dict)`。CLI 默认 preview，显式 apply 才写入。

```text
python3 -I -B <skill>/脚本/消息归档.py preview --run <运行目录> --task <科学任务文件> --actor <实际归档角色ID> --expected-root-sha <已读根SHA256> --source <来源定位JSON>
python3 -I -B <skill>/脚本/消息归档.py apply --run <运行目录> --task <科学任务文件> --actor <实际归档角色ID> --expected-root-sha <已读根SHA256> --source <来源定位JSON>
```

科学任务须处于 `started`、`completed`、`failed` 或 `stopped`，显式引用当前有效的科学合同及交付计划；实际执行归档的任务须为 `started`，具备真实收件、接受、启动时刻和 runtime 绑定。`actor` 与计划选定的执行角色一致，路径、根版本、权限和已记录额度继续核验。委托归档引用接收组长已有的同组任务，目标父目录须已存在。机械保全仅核验本次 `read_local` 与 `preserve_local` 的授权和剩余额度；生成耗用沿用既有记录，原作者及执行者的相关实际拒绝继续有效。旧合同的 fileheld 或完成标签不自动产生归档许可。

`source` 严格包含以下九个定位字段，可选增加 `tool_use_id`、`task_id`、`author_id`、`version`。示例为占位数据，实际定位与 hash 须来自已观察原件。

```json
{
  "path": "/<本地来源目录>/合成转录.jsonl",
  "line": 1,
  "record_uuid": "00000000-0000-4000-8000-000000000001",
  "pointer": "/message/content/0/input/message",
  "raw_line_sha256": "<指定完整行含LF的SHA256>",
  "payload_bytes": 123,
  "payload_sha256": "<完整文本UTF8字节的SHA256>",
  "utf8_start": 0,
  "utf8_end": 123
}
```

`path` 须为固定、绝对且已规范化的普通 JSONL 文件路径，`line` 按原始 LF 从 1 计数且不超过 1000000，`raw_line_sha256` 覆盖该行及其结束 LF；单行最多 2 MiB。`record_uuid` 须为规范化、非零 UUID，与记录 `uuid` 一致。来源记录的 `type` 和 `message.role` 均为 `assistant`；显式标记 `isApiErrorMessage=true` 的 API 错误占位返回 `message_api_error`，即使各项 hash 匹配也不能作为正文归档。其他文本的科学语义仍由作者及实际接收组长判断。

`pointer` 仅支持 `/message/content/<n>/text` 或 `/message/content/<n>/input/message`，前者对应完整 assistant text，后者须为真实 `SendMessage` 工具块且 `input.to == reader_id`。选定的完整字符串按 UTF-8 保存，最多 1 MiB；`payload_bytes` 与 `payload_sha256` 核验这些字节，`utf8_start=0`、`utf8_end=payload_bytes`，不接受片段、拼接或内部思考。可选 `tool_use_id` 核对工具块 ID；`task_id`、`author_id`、`version` 仅校验声明与任务合同一致，不能认证来源记录缺失的作者或版本元数据。CLI 定位 JSON 须为不超过 16 KiB 的 UTF-8 普通文件；非阻塞打开后核验文件类型，FIFO、设备和目录均拒绝。

归档前后核验根版本、路径绑定、源文件身份及指定原始行，允许源文件追加。新原件排他落盘；目标已有相同字节时幂等返回，内容不同则拒绝覆盖。preview 不形成原件，实际落盘或确认已有相同原件后才登记对应交付事实。成功结果包含 `material_ref`（运行内相对路径及 SHA-256）、`payload_bytes`、原 `source` 定位、`applied`、`already_present`，并明确 `author_authenticated=false`、`action_permission=false`。提交失败时，仅回收本次创建且未被外部改动的文件；外部改动保持原状，错误结果的 `applied` 可能为 `true`，须按实际结果核对保全状态。工具不修改 Root，不登记 `read_at` 或 `completed`，不重新形成科学判断；实际接收组长仍须阅读全文并另行确认。
